Сегодня про обманчивый статус `202 Accepted` и то, почему отправка письма по SMTP не должна блокировать HTTP-ответ.

---

## Как это выглядело

Пользователь в приложении на Flutter вводит email и нажимает «Получить код». Через 8 секунд экран показывает ошибку:

```text
TimeoutException after 0:00:08: Future not completed
```

А ещё через пару секунд на почту **приходит письмо с кодом**. То есть сервер всё сделал, но клиент решил, что сервер умер, и не перешёл на экран ввода кода.

---

## Что происходило на сервере

Мой эндпоинт `POST /v1/members/magic` честно возвращал `202 Accepted`, но внутри обработчика стоял обычный `await`:

```rust
repo::insert_code(&st.db, Uuid::new_v4(), member.id, &hash(&code), expires).await?;
mailer.send_code(&email, &code).await?; // <-- Жду весь SMTP-диалог прямо здесь!
Ok(())
```

Пока я тестировал локально с консольным мейлером (который просто печатал код в stdout), это занимало `0.1 мс`.

Когда появился реальный прямой MX-отправщик на Rust (`mail-send`), один вызов `send_code()` превратился в цепочку сетевых операций:

1. DNS-запрос MX-записей домена получателя.
2. TCP-подключение на 25-й порт внешнего почтового сервера.
3. `EHLO` -> `STARTTLS` -> TLS-рукопожатие.
4. Передача письма, DKIM-подпись и ожидание `250 OK`.

На всё это уходило **от 3 до 10 секунд** - а у мобильного клиента стоял жёсткий таймаут **8 секунд**.

{{< alert "comment" >}}
HTTP-статус **202 Accepted** означает, что сервер принял запрос в работу, но сама операция ещё не обязана быть завершена к моменту ответа. Если ждать внешний SMTP-сервер до отправки ответа, смысл `202` теряется.
{{< /alert >}}

---

## Решение: честный 202 Accepted через tokio::spawn

Код уже сохранён в базе, поэтому клиенту не нужно ждать, пока почтовик на другом конце интернета скажет `250 OK`. Достаточно запустить отправку в фоне:

```rust
repo::insert_code(&st.db, Uuid::new_v4(), member.id, &hash(&code), expires).await?;

if matches!(mailer, Mailer::Console | Mailer::Capture(_)) {
    // В dev и в юнит-тестах оставляю синхронно
    mailer.send_code(&email, &code).await?;
} else {
    let mailer = mailer.clone();
    let email_bg = email.clone();
    tokio::spawn(async move {
        if let Err(e) = mailer.send_code(&email_bg, &code).await {
            tracing::error!(error = %e, to = %email_bg, "failed to send magic code");
        }
    });
}
```

Ответ клиенту теперь улетает за **~15 мс** вместо 8+ секунд.

{{< alert "lightbulb" >}}
Ошибки из фоновой задачи `tokio::spawn` не попадают в обработчик HTTP-запроса, поэтому их обязательно логировать прямо внутри блока `async move` (например, через `tracing::error!`). Иначе падение SMTP останется невидимым.
{{< /alert >}}

## Три важных детали, чтобы не наступить на новые грабли

1. **Не ломайте юнит-тесты.** Если в тестах используется mock-мейлер (`Mailer::Capture`), тест сразу после вызова функции проверяет, что письмо попало в вектор. Если его тоже унести в `tokio::spawn`, тесты станут флакать из-за гонки. Поэтому mock и консоль оставляю синхронными.
2. **Ставьте таймауты внутри фоновой задачи.** Если первый MX-сервер получателя не отвечает, `connect()` без таймаута может висеть по минуте на каждой попытке. Я оборачиваю `connect` (10 сек) и `send` (15 сек) в `tokio::time::timeout`.
3. **Защита от спама уже есть.** Запись кода в БД (и проверка 60-секундного кулдауна) делается **до** `tokio::spawn`, так что повторный клик пользователя не запустит вторую отправку.

{{< alert "fire" >}}
У фоновой задачи через `tokio::spawn` есть один компромисс: при резкой остановке сервера или нехватке памяти задача в памяти может не успеть завершиться, хотя клиент уже получил `202`. Если доставка критична и её нельзя терять при рестарте, вместо голого `tokio::spawn` лучше складывать письма в таблицу-очередь (outbox) в базе данных.
{{< /alert >}}


### 📝 Проверьте себя: HTTP 202 и tokio::spawn


**1. Почему мобильное приложение падало с TimeoutException, даже несмотря на статус 202 Accepted от сервера?**

- [ ] Потому что статус 202 не поддерживается во Flutter
- [ ] Потому что сервер держал соединение открытым и ждал завершения SMTP-диалога до отправки ответа
- [ ] Потому что почтовый сервер возвращал 502 Bad Gateway
- [ ] Потому что база данных блокировалась на 8 секунд при записи кода

**2. Почему в примере для Mailer::Console и Mailer::Capture отправка остаётся синхронной (без tokio::spawn)?**

- [ ] Потому что консольный мейлер не поддерживает асинхронный Rust
- [ ] Чтобы в юнит-тестах не возникала гонка между проверкой результата и фоновой задачей
- [ ] Потому что tokio::spawn нельзя вызывать в режиме разработки
- [ ] Чтобы снизить нагрузку на DNS в тестах

**3. Что произойдёт с ошибкой, если не залогировать её внутри tokio::spawn?**

- [ ] Axum автоматически вернёт клиенту 500 Internal Server Error
- [ ] Программа немедленно запаникует
- [ ] HTTP-обработчик уже вернул 202 и не узнает об ошибке, она пропадёт незамеченной
- [ ] Tokio автоматически повторит отправку письма

**4. Зачем внутри фоновой задачи оборачивать connect и send в tokio::time::timeout?**

- [ ] Чтобы клиент быстрее получил 202 Accepted
- [ ] Чтобы фоновая задача не зависала на минуты, если внешний MX-сервер не отвечает
- [ ] Потому что без timeout tokio::spawn не компилируется
- [ ] Чтобы обойти 60-секундный кулдаун в базе данных

**5. Почему повторный клик пользователя не запустит две фоновые отправки подряд?**

- [ ] Потому что tokio::spawn дедуплицирует одинаковые задачи
- [ ] Потому что запись кода в БД и проверка 60-секундного кулдауна выполняются до tokio::spawn
- [ ] Потому что почтовый сервер сам отклоняет повторные письма
- [ ] Потому что Flutter блокирует кнопку на 10 секунд
