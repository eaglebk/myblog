> Почему асинхронный эндпоинт отправки письма заставляет мобильное приложение падать с TimeoutException, и как правильно выносить отправку по SMTP в фоновую задачу через tokio::spawn.

Сегодня про обманчивый статус `202 Accepted` и то, почему отправка письма по SMTP не должна блокировать HTTP-ответ.

---

## Как это выглядело

Пользователь в приложении на Flutter вводит email и нажимает «Получить код». Через 8 секунд экран показывает ошибку:

```text
TimeoutException after 0:00:08: Future not completed
```

А ещё через пару секунд на почту **приходит письмо с кодом**. То есть сервер всё сделал, но клиент решил, что сервер умер, и не перешёл на экран ввода кода.

---

## Что происходило на сервере

Мой эндпоинт `POST /v1/members/magic` честно возвращал `202 Accepted`, но внутри обработчика стоял обычный `await`:

```rust
repo::insert_code(&st.db, Uuid::new_v4(), member.id, &hash(&code), expires).await?;
mailer.send_code(&email, &code).await?; // <-- Жду завершения отправки по SMTP прямо здесь!
Ok(())
```

Пока я тестировал локально с консольным мейлером (который просто печатал код в stdout), это занимало `0.1 мс`.

Когда появился реальный прямой MX-отправщик на Rust (`mail-send`), один вызов `send_code()` превратился в цепочку сетевых операций: DNS-запрос MX-записи, подключение по TCP на 25-й порт, TLS-рукопожатие и передача письма до ответа внешнего почтового сервера.

На всё это уходило **от 3 до 10 секунд**, а с учётом сетевых замедлений и ограничений со стороны провайдеров в последнее время внешние TCP/TLS-соединения с зарубежными почтовыми серверами тормозят ещё сильнее. При этом у мобильного клиента стоял жёсткий таймаут **8 секунд**.

{{< alert "comment" >}}
HTTP-статус **202 Accepted** означает, что сервер принял запрос в работу, но сама операция ещё не обязана быть завершена к моменту ответа. Если ждать внешний SMTP-сервер до отправки ответа, смысл `202` теряется.
{{< /alert >}}

---

## Решение: честный 202 Accepted через tokio::spawn

Код уже сохранён в базе, поэтому клиенту не нужно ждать, пока почтовик на другом конце интернета ответит `250 OK`. Достаточно запустить отправку в фоне:

```rust
repo::insert_code(&st.db, Uuid::new_v4(), member.id, &hash(&code), expires).await?;

if matches!(mailer, Mailer::Console | Mailer::Capture(_)) {
    // В dev и в юнит-тестах жду отправки прямо здесь (без tokio::spawn)
    mailer.send_code(&email, &code).await?;
} else {
    let mailer = mailer.clone();
    let email_bg = email.clone();
    tokio::spawn(async move {
        if let Err(e) = mailer.send_code(&email_bg, &code).await {
            tracing::error!(error = %e, to = %email_bg, "failed to send magic code");
        }
    });
}
```

Ответ клиенту теперь улетает за **~15 мс** вместо 8+ секунд.

{{< alert "lightbulb" >}}
Ошибки из фоновой задачи `tokio::spawn` не попадают в обработчик HTTP-запроса, поэтому их обязательно нужно логировать прямо внутри блока `async move` (например, через `tracing::error!`). Иначе падение SMTP останется невидимым.
{{< /alert >}}

## Три важных детали, чтобы не наступить на новые грабли

1. **Не ломайте юнит-тесты.** Если в тестах используется mock-мейлер (`Mailer::Capture`), тест сразу после вызова эндпоинта проверяет, что письмо сохранилось во внутреннем буфере мока (например, в `Vec`). Если его тоже вынести в `tokio::spawn`, тесты начнут нестабильно падать из-за состояния гонки. Поэтому для mock и консоли оставляю прямой `.await`.
2. **Ставьте таймауты внутри фоновой задачи.** Если первый MX-сервер получателя не отвечает, `connect()` без таймаута может висеть по минуте на каждой попытке. Я оборачиваю `connect` (10 сек) и `send` (15 сек) в `tokio::time::timeout`.
3. **Защита от спама уже есть.** Запись кода в БД (и проверка 60-секундной паузы между отправками) делается до `tokio::spawn`, так что повторный клик пользователя не запустит вторую отправку.

{{< alert "fire" >}}
У фоновой задачи через `tokio::spawn` есть один компромисс: при резкой остановке сервера или нехватке памяти фоновая задача может не успеть завершиться, хотя клиент уже получил `202`. Если доставка критична и её нельзя терять при рестарте, вместо голого `tokio::spawn` лучше складывать письма в таблицу-очередь (outbox) в базе данных.
{{< /alert >}}
