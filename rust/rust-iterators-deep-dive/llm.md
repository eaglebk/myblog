В прошлый раз я разбирал [замыкания в Rust](../rust-closures/) и то, как компилятор перемещает захваченные переменные в анонимные структуры. Сегодня разберём итераторы. Вместе с замыканиями они дают короткие цепочки вроде `.filter().map().collect()`, которые при сборке разворачиваются в обычный цикл без лишних выделений памяти.

В JavaScript цепочка `arr.filter(...).map(...)` на каждом шаге создаёт новый промежуточный массив в куче и нагружает сборщик мусора, а в Python даже ленивые `map()` и `filter()` оборачивают каждый шаг в вызовы интерпретатора и аллокации объектов. Когда я только переходил на Rust с Go, то по привычке писал ручные циклы с `let mut out = Vec::new()`, боясь лишних накладных расходов. На деле всё наоборот: цепочка итераторов ничего не выделяет на лету и компилируется в обычный быстрый цикл.

Разберём, как это устроено: во что компилятор превращает `for`, как работают ленивые цепочки, когда хватает `std::iter::from_fn`, как возвращать `impl Iterator` из функций и в каких случаях обычный `for` всё же читается лучше.

{{< alert "comment" >}}
**Что такое ленивая цепочка?** Если коротко, это план работы без самих вычислений. В обычном «жадном» коде (как у методов массива `arr.filter().map()` в JS или генераторов списков `[... for x in arr]` в Python) каждый шаг сразу прогоняет весь массив и складывает результат во временный список. В Rust вызов `.filter(...).map(...)` не трогает ни одного элемента: он просто запоминает, что и как нужно сделать с данными. Реальная работа начинается только тогда, когда вы просите выдать результат (например, через `.collect()`, `.sum()` или цикл `for`), причём элементы идут через всю цепочку по одному за раз, без промежуточных массивов. Как это работает внутри, посмотрим во втором разделе.

## 1. Во что разворачивается цикл `for` и при чём здесь `IntoIterator`

Знакомый цикл `for item in collection` в Rust - это синтаксический сахар. При компиляции он разворачивается (чуть упрощённо, без обёртки `match` для временных значений) в `loop` с вызовом `IntoIterator::into_iter`:

```rust
// То, что пишете вы:
for item in names {
    println!("{item}");
}

// То, что видит компилятор:
let mut iter = IntoIterator::into_iter(names);
loop {
    match iter.next() {
        Some(item) => {
            println!("{item}");
        }
        None => break,
    }
}
```

Отсюда и разница между тремя способами обойти коллекцию. Стандартный `Vec<T>` (и большинство контейнеров в `std`) реализует типаж `IntoIterator` сразу тремя способами: для самого значения `Vec<T>`, для обычной ссылки `&Vec<T>` и для изменяемой ссылки `&mut Vec<T>`.

### `.iter()` или `for item in &vec`

Метод `.iter()` создаёт итератор, который выдаёт неизменяемые ссылки `&T`. Вектор остаётся у вас на руках, после цикла его можно читать и передавать дальше:

```rust
let names = vec!["Анна".to_string(), "Борис".to_string()];

for name in names.iter() {
    println!("Читаю: {name}");
}
// names по-прежнему жив и доступен
println!("Всего имён: {}", names.len());
```

### `.iter_mut()` или `for item in &mut vec`

Метод `.iter_mut()` отдаёт изменяемые ссылки `&mut T`, позволяя менять элементы на месте без создания нового вектора:

```rust
let mut scores = vec![10, 20, 30];

for score in scores.iter_mut() {
    *score += 5;
}
// scores теперь [15, 25, 35]
```

### `.into_iter()` или `for item in vec`

Вызов `.into_iter()` забирает коллекцию целиком и отдаёт вам сами значения `T`. Память самого вектора освобождается, а строки или структуры переезжают прямо в тело цикла:

```rust
let names = vec!["Анна".to_string(), "Борис".to_string()];

for name in names.into_iter() {
    // Здесь name имеет тип String, а не &String
    drop(name);
}
// Попытка обратиться к names здесь не скомпилируется: значение перемещено
```

{{< alert "fire" >}}
**Частая ловушка с `for`:** новички часто обжигаются на короткой записи `for item in items` без амперсанда. Такой цикл молча вызывает `.into_iter()` и забирает владение вектором, поэтому строчкой ниже компилятор уже запретит к нему обращаться. Если коллекция ещё пригодится после цикла, пишите `for item in &items`.
{{< /alert >}}

## 2. Ленивая модель: адаптеры ждут терминального вызова

В Rust итераторы работают по **pull-модели** (модели вытягивания), а не push-модели. Когда вы пишете цепочку вроде `.filter(...).map(...)`, данные никуда не бегут. Вместо этого каждый адаптер заворачивает предыдущий итератор в новую структуру на стеке:


### 💻 Проверяем ленивость и размер обёртки


```rust
fn main() {
    let numbers = vec![1, 2, 3, 4, 5];

    // Никаких вычислений! В памяти на стеке лежит структура Map<Iter<'_, i32>, ...>
    let doubled = numbers.iter().map(|x| {
        println!("Обрабатываю {x}");
        x * 2
    });

    println!("Размер обёртки на стеке: {} байт", std::mem::size_of_val(&doubled));
    println!("Реальный тип: {}", std::any::type_name_of_val(&doubled));
}
```

**Проверяем ленивость и размер обёртки**
- Запустите код: в выводе не появится ни одной строки «Обрабатываю ...», потому что терминальный метод не вызван.
- Размер `doubled` на стеке составляет 16 байт, а тип показывает вложенную структуру `Map<Iter<'_, i32>, ...>`.


Этот простой тест сразу снимает вопросы про «скрытые аллокации»: `size_of_val(&doubled)` покажет 16 байт на стеке (два указателя среза, а само замыкание ничего не захватывает и весит 0 байт), а `type_name_of_val` выведет вложенный тип `core::iter::adapters::map::Map<core::slice::iter::Iter<i32>, ...>`. Если не потребить `doubled`, на экран не выведется ни одной строчки из замыкания, а компилятор покажет предупреждение: типаж `Iterator` помечен атрибутом `#[must_use = "iterators are lazy and do nothing unless consumed"]`.

Вычисления запускаются только тогда, когда вы вызываете **терминальный метод** (его ещё называют *consuming adaptor*), который сам крутит `.next()` внутри себя:

- `.collect()` - собирает поток в коллекцию (`Vec`, `HashSet`, `HashMap`, `String`) и умеет останавливать цикл на первой ошибке через `collect::<Result<Vec<_>, _>>()` (подробнее я писал в заметке про [`collect()`](../rust-collect/)). А если битые элементы нужно просто пропустить и идти дальше, пригодится `.filter_map(|s| s.parse::<i32>().ok())`.
- `.fold()` и `.reduce()` - сворачивают элементы в одно итоговое значение с аккумулятором (`try_fold` делает то же самое с ранним выходом по `Result` или `Option`).
- `.sum()` и `.product()` - считают сумму или произведение элементов.
- `.find()`, `.any()`, `.all()` - останавливаются, как только нашли нужный элемент или нарушили условие (**short-circuiting**).
- `.for_each()` - прогоняет замыкание ради побочных эффектов вроде записи в лог или отправки в канал.

Именно из-за pull-модели вызов `huge_vec.iter().filter(...).map(...).take(3).collect()` обработает только столько элементов, сколько нужно, чтобы набрать первые 3 результата, а остальной миллион элементов даже не тронет.

## 3. Пишем свой `Iterator`: retry-задержки и ленивая пагинация

Чтобы любая ваша структура заработала в цикле `for` и получила доступ ко всему набору стандартных комбинаторов, достаточно реализовать типаж `std::iter::Iterator`:

```rust
pub trait Iterator {
    type Item;

    fn next(&mut self) -> Option<Self::Item>;
}
```

Один обязательный ассоциированный тип `Item` и один метод `next`. Взамен вы автоматически получаете больше 70 готовых методов вроде `map`, `filter`, `zip`, `enumerate`, `skip`, `take`, `fold` и `collect`.

### Пример 1: Генератор задержек для повторных запросов (Exponential Backoff)

Когда сервис ходит во внешний API или базу данных, при сетевых сбоях используют повторные попытки с экспоненциальной задержкой: 100 мс, 200 мс, 400 мс, но не больше заданного потолка и с ограничением числа попыток. Такой планировщик удобно оформить как `Iterator` с защитой от переполнения через `saturating_mul`:

```rust
use std::iter::FusedIterator;
use std::time::Duration;

struct RetryBackoff {
    current: Duration,
    max_delay: Duration,
    remaining: usize,
}

impl RetryBackoff {
    fn new(initial: Duration, max_delay: Duration, attempts: usize) -> Self {
        Self { current: initial, max_delay, remaining: attempts }
    }
}

impl Iterator for RetryBackoff {
    type Item = Duration;

    fn next(&mut self) -> Option<Self::Item> {
        if self.remaining == 0 { {{< golink id="rb1" />}}
            return None;
        }
        self.remaining -= 1;
        let delay = self.current.min(self.max_delay);
        self.current = self.current.saturating_mul(2).min(self.max_delay); {{< golink id="rb2" />}}
        Some(delay)
    }
}

impl FusedIterator for RetryBackoff {}
```

Здесь за ключевое поведение отвечают две строки: проверка `remaining == 0` ({{< codelink id="rb1" />}}) гарантирует, что после исчерпания попыток итератор навсегда останется пустым, а `saturating_mul(2).min(self.max_delay)` ({{< codelink id="rb2" />}}) удваивает задержку с защитой от переполнения и ограничивает её потолком. По правилам обычного `Iterator` после `None` следующий вызов `.next()` в теории может снова вернуть `Some(...)`. Маркер `FusedIterator` обещает обратное: если итератор закончился, он пустой навсегда. Для обычных итераторов без такой гарантии есть метод `.fuse()`.

### Короткий путь: `std::iter::from_fn` вместо отдельной структуры

В большинстве задач не нужно заводить отдельную структуру и руками писать `impl Iterator`. Если генератор простой и его не нужно возвращать из функции по конкретному имени типа, в стандартной библиотеке есть `std::iter::from_fn` (а для простых последовательностей от предыдущего значения - `std::iter::successors`):


### 💻 Батчи через std::iter::from_fn


```rust
fn main() {
    // Нарезаем диапазон ID [0..100) на батчи по 25 штук
    let mut cursor = Some(0u64);
    let batches = std::iter::from_fn(move || {
        let start = cursor?;
        if start >= 100 {
            cursor = None;
            return None;
        }
        let end = (start + 25).min(100);
        cursor = Some(end);
        Some(start..end)
    });

    let ranges: Vec<_> = batches.collect();
    println!("Батчи: {:?}", ranges);
}
```

**Генератор батчей через std::iter::from_fn**
- Замыкание хранит текущую позицию `cursor` и при каждом вызове `.next()` возвращает очередной диапазон `Range<u64>`.


Отдельная структура нужна, когда внутри много состояния, требуются дополнительные типажи (`DoubleEndedIterator`, `ExactSizeIterator`) или тип итератора должен светиться в публичном API.

### Пример 2: Ленивый итератор пагинации

В реальных проектах свои итераторы чаще всего пишут не для математики, а под постраничные API, курсоры баз данных или чтение батчей с диска. Вместо того чтобы выкачивать 50 страниц и складывать всё в один большой `Vec`, можно обернуть курсор в `Iterator` с небольшим буфером `VecDeque`:

```rust
use std::collections::VecDeque;
use std::iter::FusedIterator;

struct PageIter {
    next_page: usize,
    buffer: VecDeque<String>,
    done: bool,
}

impl Iterator for PageIter {
    type Item = String;

    fn next(&mut self) -> Option<Self::Item> {
        while self.buffer.is_empty() && !self.done { {{< golink id="pg1" />}}
            let items = fetch_page(self.next_page);
            if items.is_empty() {
                self.done = true;
            } else {
                self.next_page += 1;
                self.buffer.extend(items);
            }
        }
        self.buffer.pop_front() {{< golink id="pg2" />}}
    }
}

impl FusedIterator for PageIter {}
```

Пока в локальной очереди `VecDeque` есть элементы, итератор отдаёт их через `pop_front()` ({{< codelink id="pg2" />}}) без лишних обращений к сети. Как только буфер опустел, условие `while` ({{< codelink id="pg1" />}}) подгружает ровно одну следующую страницу. Поэтому вызов `PageIter::new().take(3).collect()` (полный запускаемый пример есть в интерактивных слайдах внизу) скачает только те страницы, которые нужны для первых трёх записей, и остановится.

Только помните: обычный `Iterator` синхронный, и написать `.await` внутри `next()` нельзя. Для асинхронной пагинации в `tokio` используют `futures::Stream` и крейт `async-stream`.

### Три полезных дополнительных типажа

Когда пишете свой итератор, полезно знать ещё о нескольких стандартных расширениях:

1. **`DoubleEndedIterator`** добавляет метод `next_back()`, позволяя обходить последовательность с обоих концов и открывая доступ к методам `.rev()` и `.rfind()`.
2. **`ExactSizeIterator`** добавляет метод `len()`, когда точное число оставшихся элементов известно заранее. Благодаря ему `.collect::<Vec<_>>()` выделяет память одним вызовом `Vec::with_capacity(len)` вместо серии реаллокаций по мере роста массива. Для приблизительной оценки объёма в `Iterator` также есть метод `size_hint(&self) -> (usize, Option<usize>)`.
3. **`IntoIterator`** можно реализовать для вашей собственной коллекции-обёртки, чтобы её можно было передавать прямо в `for x in &my_collection`.

{{< alert "lightbulb" >}}
**Нюанс с `ExactSizeIterator`:** адаптер `.map()` сохраняет точную длину (и `collect::<Vec<_>>()` выделит память за одну аллокацию), а вот `.filter()` её сбрасывает - компилятор не знает заранее, сколько элементов пройдёт проверку предиката.
{{< /alert >}}

### Возврат ленивого итератора из функции (`-> impl Iterator`)

Вместо того чтобы собирать внутри функции промежуточный `Vec<T>`, проще вернуть ленивый итератор. Пусть вызывающий код сам решает, складывать всё в вектор или остановиться на первом совпадении:

```rust
fn non_empty_lines(text: &str) -> impl Iterator<Item = &str> + '_ {
    text.lines()
        .map(str::trim)
        .filter(|line| !line.is_empty())
}
```

Обратите внимание на `+ '_`: возвращаемый итератор читает входную строку `text`, поэтому компилятору нужно подсказать, что итератор живёт не дольше этой строки (начиная с Rust 2024 edition компилятор понимает это сам, и писать `+ '_` уже не обязательно). Никакого `Vec` внутри функции не создаётся.

## 4. Нулевая стоимость абстракций: итераторы против цикла по индексу

Кто писал на C# или Java, привык с подозрением смотреть на длинные цепочки методов: хотя LINQ и Java Streams тоже ленивые, там адаптеры выделяют объекты в куче, ходят через интерфейсы и часто пакуют примитивы (boxing), из-за чего проигрывают обычному циклу `for`.

В Rust всё иначе по двум причинам:

1. **Мономорфизация и инлайнинг.** Каждый адаптер (`Filter<Iter<i32>, F>`, `Map<..., G>`) - это конкретный тип на этапе компиляции, а не виртуальный вызов через `dyn Iterator`. Компилятор видит всю цепочку целиком, встраивает тела `.next()` и замыканий друг в друга и собирает их в один плоский цикл.
2. **Устранение проверок границ (Bounds Check Elimination).** Взгляните на два способа просуммировать срез:

```rust
// Способ 1: ручная индексация
let mut sum = 0;
for i in 0..slice.len() {
    sum += slice[i];
}

// Способ 2: итератор по срезу
let sum: i32 = slice.iter().sum();
```

При обращении `slice[i]` Rust обязан гарантировать, что индекс не вылетел за пределы буфера. Для простого `0..slice.len()` оптимизатор ещё может доказать безопасность, но стоит появиться смещению вроде `slice[i + 1]` или шагу по два элемента, в бинарник тут же попадают инструкции проверки длины и условные переходы к панике. В таких случаях идиоматичные `slice.windows(2)` или `slice.chunks_exact(2)` решают задачу без единой проверки границ в теле цикла.

Внутренний итератор среза `std::slice::Iter` устроен иначе: он хранит два сырых указателя - на текущий элемент и на конец среза - и на каждом шаге просто сдвигает указатель вперёд внутри `unsafe`-обёртки, корректность которой уже доказана при создании среза. Никаких проверок границ на итерации нет, а ровный цикл без лишних веток компилятор легко переводит в векторные SIMD-инструкции.

.sum() ;; .sum() ;; add     v1.4s||add     v2.4s||subs||b.ne ;; Накапливает сумму в двух параллельных регистрах-счётчиках и крутит единый цикл без вызовов функций и выделения памяти.
{{< /code-before-after >}}

Посмотреть функцию целиком вместе с остальной частью кода можно на [Godbolt (`rustc 1.95.0`, `--edition 2021 -O --target aarch64-unknown-linux-gnu`)](https://godbolt.org/z/Kjh19eMv8).

Здесь показан главный цикл функции, который обрабатывает по 8 чисел за раз (если длина массива не кратна 8, остаток в конце досчитывается обычным поэлементным циклом). При этом стоит помнить о двух вещах:

- **С дробными числами (`f32` / `f64`) такой трюк сам не сработает.** Целые числа можно складывать в любом порядке, и сумма всегда совпадёт. А вот у `f32` и `f64` из-за погрешности округления от перемены мест слагаемых результат может чуть-чуть измениться. Компилятор не имеет права менять точность без вашего ведома, поэтому `.sum::<f64>()` складывает числа строго по очереди и не разгоняется через SIMD так же легко, как `i32`.
- **Итераторы работают в одном потоке.** Весь этот SIMD-разгон происходит внутри одного ядра процессора. Если данных много и хочется загрузить все ядра сразу, возьмите крейт `rayon`: достаточно заменить `.iter()` на `.par_iter()`, и цепочка сама разделит работу между потоками.

## 5. Четыре частые ловушки с итераторами

### Двойные ссылки `&&T` в `.filter()`

Если вы хоть раз писали `nums.iter().filter(|&&x| x > 0)`, то наверняка удивлялись, откуда взялись два амперсанда. Логика здесь простая:
- `nums.iter()` выдаёт элементы типа `&i32`.
- Метод `.filter()` не может отдавать элемент в замыкание по значению, иначе его потом нельзя передать дальше по цепочке. Поэтому в проверку всегда приходит ссылка `&Self::Item`, что для `&i32` даёт `&&i32`.

Чтобы не возиться с двойным разыменованием в простых типах вроде чисел, удобно вставить `.copied()` (или `.cloned()` для типов с `Clone`):

```rust
let sum: i32 = nums.iter().copied().filter(|&x| x > 0).sum();
```

### Попытка изменить коллекцию во время итерации

Код вроде такого не пропустит borrow checker:

```rust
let mut items = vec![1, 2, 3];
for &x in &items {
    if x == 2 {
        items.push(99); // Ошибка: нельзя мутабельно заимствовать items, пока по нему идёт &items
    }
}
```

{{< alert "comment" >}}
**Почему borrow checker это запрещает:** в C++ добавление элемента в вектор во время обхода может вызвать реаллокацию буфера в куче, после чего указатели внутри итератора начинают смотреть в уже освобождённую память (*iterator invalidation*). В Rust для фильтрации на месте используют `items.retain(|&x| x != 2)`, для извлечения подходящих элементов с удалением из исходного вектора - `items.extract_if(.., |x| *x == 2)` (стабилизирован в Rust 1.87), а для добавления новых элементов сначала собирают добавки в отдельный буфер и вливают через `items.extend(new_items)`.
{{< /alert >}}

### Потеря итератора после `.take(n)`: выручает `.by_ref()`

Почти все адаптеры (`take`, `skip`, `map`) принимают `self` по значению и поглощают исходный итератор. Если вы хотите откусить первые 3 элемента как заголовок, а затем продолжить читать тот же самый итератор дальше, одолжите его по мутабельной ссылке через `.by_ref()`:


### 💻 Чтение заголовка через .by_ref()


```rust
fn main() {
    let mut it = [10, 20, 30, 40, 50].into_iter();
    let header: Vec<i32> = it.by_ref().take(2).collect();
    let rest: Vec<i32> = it.collect();

    println!("header = {:?}, rest = {:?}", header, rest);
}
```

**Отделяем заголовок через .by_ref()**
- `take(2)` заимствует итератор по мутабельной ссылке, поэтому после него `it` остаётся живым и отдаёт оставшиеся элементы `[30, 40, 50]`.


### Бесконечный итератор без ограничителя

Если у собственного итератора в `next()` всегда возвращается `Some(...)` (как у бесконечного генератора чисел `0..`), вызов `.collect()`, `.count()` или `.last()` на нём повесит поток навсегда. Перед терминальными методами бесконечные генераторы обязательно ограничивают сверху через `.take(n)` или `.take_while(...)` (методы вроде `.find(...)` или `.any(...)` завершатся только в том случае, если искомый элемент гарантированно встретится в потоке).

## 6. Когда писать `for`, а когда цепочку итераторов

Итераторы не обязаны заменять каждый цикл в проекте. На практике я придерживаюсь простого правила:

- **Выбираю цепочку итераторов**, когда задачу можно выразить как линейный конвейер (фильтрация, преобразование, поиск, свёртка в коллекцию или сумму) без лишних `let mut` переменных.
- **Выбираю обычный `for`**, когда внутри цикла нужны сложные ранние выходы (`return`, `break` из внешнего цикла), проброс ошибок через `?` в несколько мест или обновление сразу нескольких локальных переменных. Пытаться втиснуть такую логику в `try_fold` - верный способ сделать код нечитаемым.

Все эти примеры - режимы заимствования, `from_fn` и ленивую пагинацию - можно покрутить и запустить прямо в браузере:


### 💻 Устройство и практика итераторов в Rust


#### Шаг 1

```rust
fn main() {
    let mut numbers = vec![10, 20, 30];

    // 1. Заимствование по &T (эквивалентно for num in &numbers)
    for num in numbers.iter() {
        println!("По ссылке (&T): {num}");
    }

    // 2. Изменение на месте по &mut T (эквивалентно for num in &mut numbers)
    for num in numbers.iter_mut() {
        *num += 5;
    }
    println!("После iter_mut: {:?}", numbers);

    // 3. Поглощение коллекции: for num in numbers делает то же самое
    for num in numbers.into_iter() {
        println!("Во владение (T): {num}");
    }
    // Здесь numbers уже перемещён, обратиться к нему нельзя
}
```

**Три режима итерации и IntoIterator**
- `.iter()` (или `for x in &vec`) выдаёт `&T` и оставляет коллекцию нетронутой.
- `.iter_mut()` (или `for x in &mut vec`) выдаёт `&mut T` для изменения элементов на месте.
- `.into_iter()` (или `for x in vec`) забирает владение коллекцией и отдаёт значения `T`.


#### Шаг 2

```rust
fn main() {
    let raw_inputs = ["10", "20", "bad_input", "40"];

    // Цепочка ленива: пока нет терминального метода, замыкания не запускаются
    let lazy_pipeline = raw_inputs
        .iter()
        .inspect(|s| println!("Читаю: {s}"))
        .map(|s| s.parse::<i32>());

    println!("Пайплайн создан, но ещё ничего не вычислено!");

    // collect::<Result<Vec<_>, _>>() остановится на первой ошибке и не дойдёт до "40"
    let parsed: Result<Vec<i32>, _> = lazy_pipeline.collect();
    println!("Результат разбора: {:?}", parsed);

    // .copied() убирает лишний уровень ссылки (&i32 -> i32)
    let nums = [1, -2, 3, 4];
    let positive_sum: i32 = nums.iter().copied().filter(|&x| x > 0).sum();
    println!("Сумма положительных: {positive_sum}");
}
```

**Ленивые вычисления и short-circuiting**
- Вызовы `.map()`, `.inspect()`, `.filter()` только оборачивают итератор в новую структуру.
- Работа начинается только при вызове терминального метода (`collect`, `sum`, `find`).
- `collect::<Result<Vec<_>, _>>()` прерывает обход сразу на первом `Err`, не тратя время на хвост коллекции.


#### Шаг 3

```rust
use std::iter::FusedIterator;
use std::time::Duration;

struct RetryBackoff {
    current: Duration,
    max_delay: Duration,
    remaining: usize,
}

impl RetryBackoff {
    fn new(initial: Duration, max_delay: Duration, attempts: usize) -> Self {
        Self { current: initial, max_delay, remaining: attempts }
    }
}

impl Iterator for RetryBackoff {
    type Item = Duration;

    fn next(&mut self) -> Option<Self::Item> {
        if self.remaining == 0 {
            return None;
        }
        self.remaining -= 1;
        let delay = self.current.min(self.max_delay);
        self.current = self.current.saturating_mul(2).min(self.max_delay);
        Some(delay)
    }
}

// Гарантируем, что после исчерпания попыток итератор всегда будет возвращать None
impl FusedIterator for RetryBackoff {}

fn main() {
    let attempts = 5;
    let schedule: Vec<Duration> =
        RetryBackoff::new(Duration::from_millis(100), Duration::from_millis(500), attempts)
            .collect();
    println!("План задержек retry: {:?}", schedule);
}
```

**Собственный Iterator на примере Exponential Backoff**
- Для превращения структуры в итератор достаточно задать `type Item` и метод `next`.
- `saturating_mul` и потолок `max_delay` защищают от переполнения, а `remaining == 0` позволяет реализовать `FusedIterator`.


#### Шаг 4

```rust
use std::collections::VecDeque;
use std::iter::FusedIterator;

// Имитация удалённого API: отдаёт по 2 элемента на страницу
fn fetch_page(page: usize) -> Vec<String> {
    match page {
        p if p == 0 => vec!["user_1".into(), "user_2".into()],
        p if p == 1 => vec!["user_3".into(), "user_4".into()],
        p if p == 2 => vec!["user_5".into()],
        _ => vec![],
    }
}

struct PageIter {
    next_page: usize,
    buffer: VecDeque<String>,
    done: bool,
}

impl PageIter {
    fn new() -> Self {
        Self { next_page: 0, buffer: VecDeque::new(), done: false }
    }
}

impl Iterator for PageIter {
    type Item = String;

    fn next(&mut self) -> Option<Self::Item> {
        while self.buffer.is_empty() && !self.done {
            println!("-> Запрашиваю страницу {}", self.next_page);
            let items = fetch_page(self.next_page);
            if items.is_empty() {
                self.done = true;
            } else {
                self.next_page += 1;
                self.buffer.extend(items);
            }
        }
        self.buffer.pop_front()
    }
}

impl FusedIterator for PageIter {}

fn main() {
    // Загружаем только первые 3 записи: страница 2 даже не будет запрошена!
    let first_three: Vec<String> = PageIter::new().take(3).collect();
    println!("Получено записей: {:?}", first_three);
}
```

**Практика: ленивый итератор пагинации**
- Итератор запрашивает следующую страницу только тогда, когда локальный буфер `VecDeque` опустел.
- Благодаря `.take(3)` лишние сетевые или дисковые запросы для оставшихся страниц не выполняются вообще.


#### Шаг 5

```rust
// Возвращаем ленивый итератор без создания промежуточного Vec
fn non_empty_lines(text: &str) -> impl Iterator<Item = &str> + '_ {
    text.lines().map(str::trim).filter(|line| !line.is_empty())
}

fn main() {
    // 1. std::iter::from_fn - нарезка ID на батчи без отдельной структуры
    let mut cursor = Some(0u64);
    let batches = std::iter::from_fn(move || {
        let start = cursor?;
        if start >= 100 {
            cursor = None;
            return None;
        }
        let end = (start + 25).min(100);
        cursor = Some(end);
        Some(start..end)
    });
    println!("Размер обёртки from_fn на стеке: {} байт", std::mem::size_of_val(&batches));
    println!("Батчи ID: {:?}", batches.collect::<Vec<_>>());

    // 2. Ленивый парсинг строк без аллокаций
    let log = "\n  INFO start \n\n  WARN disk 85% \n";
    let lines: Vec<_> = non_empty_lines(log).collect();
    println!("Строки лога: {:?}", lines);

    // 3. Скользящее окно windows(2) вместо ручного slice[i + 1]
    let temps = [18, 21, 19, 24];
    let diffs: Vec<i32> = temps.windows(2).map(|w| w[1] - w[0]).collect();
    println!("Дельты температур: {:?}", diffs);
}
```

**Идиомы стандартной библиотеки: from_fn, impl Iterator и windows**
- `std::iter::from_fn` заменяет отдельный `struct + impl Iterator` для компактных генераторов.
- `-> impl Iterator<Item = &str> + '_` возвращает ленивый поток, не выделяя `Vec` в куче.
- `slice.windows(2)` заменяет ручную индексацию `slice[i + 1]` без проверок выхода за границы.
